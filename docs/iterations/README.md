# 迭代工作流

适用于每轮功能开发：需求细化 → 必要的技术设计 → PR 计划 → 分 PR 实现与评审 → 迭代验收。

## 文档组织

固定入口为[当前迭代](current.md)，只记录当前阶段、当轮文档链接、当前 PR／下一步及阻塞事项。切换迭代时更新该入口，保留各轮目录。

每轮使用 `docs/iterations/<编号>-<主题>/`，按需创建：

| 文件 | 内容 |
|---|---|
| `spec.md` | 本轮范围、用户行为、异常边界、验收条件、待确认问题 |
| `design.md` | 技术方案、接口／数据／状态变化、关键取舍与风险 |
| `plan.md` | PR 拆分、依赖、状态、链接与验证证据；本轮完成后的验收结论 |

沿用的需求或设计直接引用来源，只写本轮补充与变化。需求基线已足够明确时，spec 可仅引用相关章节及验收 ID；design 按技术复杂度补充。目录和文件在该轮启动时创建，不提前铺空白文档。

全局资料各有用途：[需求](../requirements.md)定义产品行为，[路线图](../roadmap.md)安排顺序，[架构](../architecture.md)说明跨模块设计，[验收索引](../acceptance.md)关联场景。迭代结论改变全局约定时同步更新，历史 spec／design 保留当时上下文。

## 开发前

1. 整理本轮 spec，逐项澄清影响实现的问题；未决问题标明影响范围。
2. 有技术设计需要时编写 design doc；重要取舍关联决策记录。
3. 编写 PR 计划，明确每个 PR 的单一目标、改动边界、依赖及验证方式。

需求确认与既有授权沿用项目约定，不额外增加逐次编辑或测试审批。

## PR 拆分与执行

- 一个功能迭代通过多个 PR 逐步完成，每次只实现当前 PR 的范围。
- 每个 PR 聚焦一个可说明、可验证的目标；必要的测试和文档随对应改动交付。
- 无关重构、格式化、依赖升级单独安排；按评审负担拆分，不设机械的代码行数门槛。
- 每个 PR 保持可构建、可检查，明确依赖及中间能力的限制，不宣称整个迭代已完成。
- 在 plan 中记录 PR 状态：待开发、开发中、待评审、修改中、已合并；本地完成不等于已创建或合并 PR。
- PR 说明包含变更目的、范围、验证结果和必要限制，并链接本轮 spec／design。处理评审反馈后同步计划与相关文档。

按依赖逐步推进，不提前生成整轮功能代码再拆 PR。创建、推送与合并遵循用户授权及仓库约定，不默认自动合并。

用户选择仅本地开发时，用独立分支、提交和差异保留同样的评审单元；无需等待远端配置，不将本地提交记为远端 PR 已创建或已合并。

## 迭代收尾

按 spec 验收整个使用流程，在本轮 plan 汇总 PR、证据及结论，再更新当前迭代入口。新增或调整验收场景时更新全局验收索引；PR 合并、真实环境验证和用户验收分别记录。
