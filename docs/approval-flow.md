# 请求审阅与钱包确认流程

状态：2026-11-20 用户已确认页面信息、状态修复与交易确认流程；尚未实现。交易属迭代 3，连接属[迭代 2](iterations/02-connection-session/spec.md)。本文维护页面信息与交互，数据及生命周期约束沿用[需求 §5～8](requirements.md#5-连接钱包与-session)；协议和兼容细节随对应 PR 验证。

## 页面先展示什么

已有浏览器管理授权时，先加载原请求详情，再呈现钱包状态。未授权时沿用本机授权流程，不提前泄露受保护的请求内容。页面加载、查询与恢复不自动打开钱包弹窗。

| 信息 | 呈现与含义 |
|---|---|
| 请求来源 | 显示 Codex、WorkBuddy 或具体 CLI 名称，标明“调用方提供”；不宣称已验证应用身份 |
| 交易意图 | 独立显示“AI／调用方描述”；不能代替实际交易参数，也不表示 Bridge 已验证描述与交易一致 |
| 实际交易 | 显示完整可查看／复制的发送地址、to、原生币 value、data 和已指定费用；原始 data 可展开查看，未解码时明确标注 |
| 网络 | 并列显示“交易要求网络／chainId”和“钱包当前网络／chainId”；不匹配时阻止提交，提供明确指向目标网络的切换操作 |
| 账户与钱包 | 展示 Session 固定的钱包和发送地址，以及 Provider 实际暴露的账户状态；发送地址不可用时阻止提交，引导用户在钱包中切换／授权 |

gas limit 是上限，不是实际消耗；费用展示区分 client 提供、估算与未指定。未提供时显示“由钱包估算”，不凭空补值；钱包支持的传统 gasPrice 或 EIP-1559 费用字段按实际请求展示，不强制每项都有。最终费用在钱包确认中核对。

value 表示原生币数量，合约调用的 value 为零不能显示为“没有资产支出”。未知币种不猜为 ETH。ABI 解码沿用后续扩展安排；增加后保留原始 data、说明 ABI 来源，解码成功不表示安全。

## 交易交互

1. 打开原请求页，显示来源、意图、实际参数及当前请求状态；页面自身承担 Bridge 侧审阅。
2. 恢复 Session 固定的钱包。需要站点授权或解锁时，由用户点击相应操作；不静默换钱包。
3. 网络不匹配时，用户点击“切换到 <目标网络>”；账户不符合时，用户在钱包中切换／授权。修复后自动更新原页面，保留请求与审阅内容。切链失败或目标网络不支持时继续阻止提交，明确反馈原因，不自动添加网络。
4. 条件满足后，启用“在钱包中确认并发送”。点击时重新核对账户、chainId、请求有效性和执行归属，再调用钱包。
5. 钱包内由用户最终确认签名与发送；等待期间禁用重复提交。拒绝、错误及结果回到原请求页，按实际结果显示，不重复创建请求。

切换网络只改变钱包实际状态，不修改交易或 Session 的目标网络。交易内容或发送账户需改变时，沿用取消旧请求并重新创建的规则。首次切链后取消请求不自动把钱包切回，以免覆盖用户后续操作。

| 页面状态 | 可执行操作 |
|---|---|
| 钱包未就绪 | 连接／解锁或显式恢复固定钱包；交易提交禁用 |
| 网络不匹配 | 提供切换目标网络；交易提交禁用 |
| 发送账户不可用 | 引导在钱包切换／授权后重新检查；交易提交禁用 |
| 满足条件且轮到本请求 | 用户审阅后请求钱包确认；仍可拒绝请求 |
| 等待钱包 | 展示等待状态；不重复打开确认，不宣称能撤回钱包中已有操作 |
| 已取消／过期／已完成 | 展示真实结果；旧页面不能继续提交；hash 仅表示已发送 |

## 技术实现边界

- Client 提供来源名称、自然语言说明和原始交易；服务校验 Session 与参数一致并冻结请求。页面通过管理权限读取，不把链接里的字段当成交易事实。
- 前端从 Session 对应 Provider 查询 `eth_accounts`／`eth_chainId`，订阅变化事件；变动后使就绪状态失效，提交前再读。Provider 可暴露多个授权账户，不将第一个地址视为钱包唯一“当前账户”；标准接口不保证读取钱包内部 UI 的单独选中项，兼容规则需用 MetaMask／Fluent 实测。
- 前端调用钱包前，服务原子检查权限、请求状态及执行归属；持久化必要交接状态，再使用固定的 `from`／`chainId` 调用。具体竞争协议在各实现迭代细化，不能以按钮禁用代替后端检查。
- 钱包结果回传按请求幂等保存；中断与迟到结果遵守既有恢复规则，不自动重发。Bridge 服务不增加业务 RPC、解码或查链职责。

## 与首次连接的关系

首次连接尚未完成时，client 可能还没有可提交的完整交易。连接页先展示来源、连接用途（如有）、目标网络和钱包／账户选择，使用“连接钱包”“同意连接”等动作；技术上的 Session 由系统管理，不要求用户理解“建立 Session”。

有有效 Session 的交易请求直接进入上述交易审阅流程。两类页面使用相同的信息呈现与状态修复原则，但连接同意和每笔交易确认各有含义，不能相互替代。首次连接的具体确认时点在迭代 2 对应 PR 前细化。
